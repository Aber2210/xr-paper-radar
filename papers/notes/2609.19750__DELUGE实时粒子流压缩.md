# DELUGE：让多用户 VR 真正"同时摸到同一滩水"

## 一句话结论
DELUGE 是首个把**物理仿真粒子的时间相干性与速度可预测性**当作压缩先验的流式编解码架构，在 Apple Vision Pro 上端到端实现了 65K 粒子、60 fps 的**双向**实时交互，把 G-PCC 的解码延迟从 31 ms 压到 2.5 ms（≈20×），把 Draco 的编码延迟从 9.8 ms 压到 1.7 ms（≈6×）。

## 要解决的问题

社交 VR 与数字孪生的核心诉求是"多用户在同一份仿真状态上双向交互"——你搅动水流，我这边立刻看到。这条链路的瓶颈不在渲染，而在**服务端仿真 → 每个客户端**的大规模粒子数据传输。

现有点云压缩标准（MPEG G-PCC / TMC13、Google Draco）的设计前提是**静态几何结构**：它们为一次性的静态点云优化八叉树划分与熵编码。直接套用到逐帧变化的粒子流时，**编码延迟超过一帧的预算（60 fps 下 16.67 ms）**，链路直接不成立。

| 阻塞点 | 具体表现（论文 Table 3） |
|---|---|
| G-PCC 编码 | 65K 粒子 46.6 ms / 帧（超出 16.67 ms 预算 2.8×） |
| G-PCC 解码（Vision Pro 端） | 31.0 ms / 帧（超出预算 1.9×） |
| Draco 编码 | 65K 粒子 9.8 ms / 帧（勉强，但 RD 效率差） |

## 方法详解

DELUGE 的三个技术组件，全部针对"仿真粒子"而非"通用点云"的统计特性：

### 1. 速度自适应位分配（Velocity-Adaptive Bit Allocation）
物理仿真中**高速运动的粒子在感知上被运动模糊掩蔽**，人眼分辨不出其精确位置。因此把快速粒子提升到八叉树更浅的节点、分配更少比特。

> 论文 Table 4 消融（262K 粒子，B=12）：开启后 I 帧 bppf 从 29.06 降到 23.55（**-19.0%**），D1 PSNR 反而 +0.18 dB，I 帧编/解码从 21.0/13.1 ms 降到 16.2/8.1 ms。

### 2. 轴分离 Planar ANS 熵编码（Axis-Separated Planar ANS）
粒子坐标三轴的分布偏置并不相同（例如重力方向分布更集中）。分离建模后：bppf 从 6.87 降到 5.77（约 -16%），且支持**三路并行解码**。

### 3. 扁平反量化查找表（Flat Inverse-Quantization LUT）
用 O(N) 的数组访问替换八叉树遍历，解码退化为"ANS 解码 + ZigZag 反演"的**单循环**，可被编译器自动 SIMD 向量化。

> 消融：LUT 使平均解码从 6.1 ms 降到 5.6 ms，且是能在 WebAssembly 里跑满的关键。

### I/P 帧结构
关键帧（I 帧）完整编码；中间帧（P 帧）只对**粒子 ID 对应的增量**编码。因为仿真器天然保持跨帧粒子 ID 不变，delta 编码极其高效：**P 帧 bppf 仅为 I 帧的 15–30%**（Table 2）。

## 实验与结果

**数据**：MLS-MPM（Moving Least Squares Material Point Method）流体仿真，APIC 传输 + 二次 B 样条；3 档粒子数 65K/131K/262K × 10 序列 × 600 帧；Tait 状态方程（K=2000, ρ₀=1.0, γ=5），60 fps。

**指标**：D1 PSNR（点对面几何质量）、BD-Rate、每帧编解码耗时。

| 指标（262K 粒子） | DELUGE | G-PCC | Draco |
|---|---|---|---|
| BD-Rate（vs G-PCC，全 I+P） | **−73.5%** | 基准 | — |
| BD-Rate（vs Draco，全 I+P） | **−72.8%** | — | 基准 |
| 最高 D1 PSNR | ~100 dB（近无损） | ~95 dB | ~100 dB（仅高码率） |

| 每帧耗时（ms，65K） | 桌面编码 | 桌面解码 | Vision Pro 解码 |
|---|---|---|---|
| G-PCC | 46.6 | 28.2 | 31.0 |
| Draco | 9.8 | 3.4 | — |
| **DELUGE（I / P）** | **4.4 / 1.7** | **2.3 / 1.4** | **2.5 / 1.6** |

**端到端部署**：服务端 M2 Max 编码关键帧 4.4 ms → WebSocket 广播 → Vision Pro 端 8.4 ms 内完成解码并渲染，双手裸手追踪直接反馈进共享仿真。

**用户研究**：Apple Vision Pro 上 N=16 的被试内实验，对比 DELUGE 系统与 TMC13 系统，在**延迟相关的感知项与协作项**上显著更优（Wilcoxon 符号秩，r = .62–.83）。

## 创新点与贡献

1. **把"仿真粒子的物理先验"而非"通用点云的几何先验"作为压缩基础**——这是整个工作的立身之本，也是它能做到 sub-frame 延迟的根因。
2. 明确区分了**被动观看流媒体**（DASH、V-PCC 转码）与**双向交互流媒体**两类需求，指出前者的方法无法迁移到后者。
3. 解码路径完全由查表与位运算构成，因此能原样编译到 WebAssembly + SIMD（解码约 1.2× 原生耗时，输出**逐比特一致**），覆盖浏览器与原生两端。

## 局限与风险

- **依赖仿真器提供的跨帧粒子 ID**。论文在 8iVSLF / Owlii 真实采集点云上做了边界测试：只能用 I 帧路径，解码仍快 21×（47–57 ms vs 1019–1166 ms），但**码率反而落后于帧内基线**（15.46 bppf @ 60.12 dB）。作者明确指出瓶颈是 **ID 分配，不是压缩算法**——这决定了 DELUGE 短期内无法用于实拍点云。
- 用户实验在 **LAN 内**完成，WAN 下的丢包与抖动未评估。
- 协作二人组恒为"一名实验者 + 一名被试"，社交亲近度可能抬高协作评分。
- 未开源（仅 TVCG/ISMAR 录用，无代码链接）。
