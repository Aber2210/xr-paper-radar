# JOVE-ICE：面向 AI 眼镜的意图引导云–边–端协同框架

## 一句话结论
把 AI 眼镜请求路由写成带质量约束的成本优化，三级级联按「能处理该请求的最省资源层」匹配——真实请求里 > 30% 是设备控制类，9.6% 端侧直接消化、21.7% 回流手机（中位 43 ms / P99 74 ms），SuperGlasses TTFT −13% / E2E −7.2% / token −14.8%（准确率 45.46→42.49）。

## 要解决的问题
AI 眼镜的算力、电量与网络远弱于手机，但用户要求会话级延迟；现有框架多在堆功能、且研究偏重视频类能力，对「简单但高频」的请求缺乏成本控制。作者采集真实眼镜请求后发现，设备控制类指令占交互的 30% 以上，这类请求本可在端侧闭环，却常被送进云端大模型。以固定路由（全部走 Tool-Augmented Subagent）为基线，SuperGlasses 上 TTFT 为 4.5251 s、E2E 6.6057 s、每样本 4575.8 token，WearVQA 上为 2.2942 s、3.2070 s、2641.0 token。

## 方法详解
把请求路由写成带质量约束的优化：$\min\mathbb{E}[T_{\text{e2e}}(q,\pi)]+\lambda\mathbb{E}[C_{\text{token}}(q,\pi)]$，约束 $Q(q,\pi)\geq Q_{\text{base}}(q)-\epsilon$，即允许极小质量损失换延迟与 token。三级级联按「能处理该请求的最省资源层」匹配：T1 在眼镜上跑 CNN 关键词唤醒（log-Mel 输入、6 个封闭触发词、保守阈值 $\theta_{\text{kws}}$，命中即本地执行、不出网）；T2 在配对手机上做 VAD + ASR，再对 11 条设备控制命令词典做确定性字符串匹配 $f_{\text{match}}(T,\mathcal{K})$，命中就直接经蓝牙回传指令；T3 在云端用三个独立分类器：MacBERT-base 的设备控制意图（12 类：11 命令 + OTHER，另带 slot head 抽取应用名/联系人/时间并做意图-槽位一致性校验）、XLM-R-base 的视觉需求二分类（$p_v(\text{NEED\_IMAGE}\mid T)\geq\gamma$ 才抓帧）、MacBERT-large 的 SIMPLE/COMPLEX 二分类。会话管理用硬触发（显式终止词、意图突变）加软触发 $S=w_t\Delta t_{\text{inactive}}+w_d\mathbb{I}_{\text{off-body}}$，$S\geq\tau$ 即归档并新开会话，实验中 $w_t=1$、$w_d=60$、$\tau=120$ s。三个 subagent（文本对话、多模态感知、工具增强）由意图组合激活，工具增强支路接入 skill/API/MCP/RPA；图像帧仅在 NEED_IMAGE 且设备有相机时按需上传。

## 实验与结果
- 设备控制类请求占比：真实请求中 >30%
- 端侧直接消化：9.6% 的请求由 T1/T2 处理，延迟接近 0
- T3 回流 T2：21.7% 的请求被云端设备控制分类器判给手机执行，中位延迟 43 ms、P99 74 ms
- SuperGlasses：TTFT 4.5251 s → 3.9065 s（约 -13%），E2E 6.6057 s → 6.1277 s（-7.2%），token 4575.8 → 3897.4（-14.8%），准确率 45.46% → 42.49%
- WearVQA：TTFT 2.2942 s → 1.9946 s，E2E 3.2070 s → 2.8711 s（-10.5%），token 2641.0 → 2334.8（-11.6%），准确率 51.88% → 50.52%
- WearVox 五任务均值：任务分 48.96 → 51.25，TTFT -15.2%，E2E -14.5%，token -11.3%
- 意图分类器并行开销：12.375–13.228 ms/请求（三个数据集）
- 会话边界（199 轮）：Split 精确率 94.29%、召回 97.06%、F1 95.65%；Continue 99.39% / 98.79% / 99.09%

## 创新点与贡献
- 相对 VisionClaw（手机主要做数据流、计算仍集中在设备与云）与「意图感知的语义 agent 通信」（意图只用于决定传输什么），JOVE-ICE 把意图当作跨三层的路由信号：封闭词表 + 模板匹配 + 神经分类的级联决定「在哪算」，再由意图组合决定「谁来算」（三个 subagent + 会话管理）
- 它的形式化把「避免不必要的跨层传输与过度推理」写成带质量下界的延迟/token 联合目标，而不是单纯把任务卸载到边缘

## 局限与风险
- 作者自述的代价是准确率下降 2.97 与 1.36 个百分点，原因是隐含视觉问题被判成非视觉（如「仙人掌为什么形状不同」未取图），回答缺少视觉证据
- 我们另看出：端到端只对比一个基线 FR，且 FR 全部走最重的工具增强支路，属于偏弱对照
- 正文宣称降低带宽与能耗，但只报 token 与延迟，没有功耗或上行字节实测
- CascadeEval 仅 428 条、来自自家三种机型，分布代表性有限
- 云端三分类器与 27B 模型仍需 2×RTX4090 与 2×A100，端侧省下的只是「不必调用」，并非把能力搬上眼镜
