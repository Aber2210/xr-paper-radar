# Cross3DGS：从工作站到移动设备的统一 Vulkan 3D 高斯泼溅训练

## 一句话结论
以同一 Vulkan 数值更新加 256 条设备 schedule，八种跨六厂商 GPU 全部跑完 30k 步标准训练，跨设备 PSNR 差异 <0.07 dB。

## 要解决的问题
手机、平板与智能眼镜拍完 3DGS 场景仍要传回 CUDA 工作站训练，无法在采集设备上完成，也就无法保留隐私、去掉往返或离线使用。把 kernel 改写成跨厂商着色语言并不够：subgroup 宽度、float32 atomic add、storage-buffer 上限与批量命令提交的可靠性在不同 GPU 与 driver 上不同，直接决定一个名义等价的训练步能否执行并返回正确更新。现有可移植训练器 VkSplat 与 Brush 在部分移动 GPU 上根本跑不完标准质量训练。

## 方法详解
保留一个优化器 U(theta, I)（投影、tile binning 与排序、alpha 合成、损失、梯度、Adam；MCMC 细化在 U 之外），把「怎么在 GPU 上执行 U」抽象成六个选项：梯度方法（4 种 work assignment 乘 3 种 merge，共 8 值）、命令提交（batched 8 updates 或 fenced）、训练图像（resident 或 streamed）、radix sort（subgroup 或 portable）、projection+Adam（fused 或 split）、pair dispatch（indirect 或 direct），共 256 条 schedule。第一步用 13 条 feasibility rule 排除已知跑不对的 schedule：5 条读设备限制（subgroup 宽度、shared memory、storage-buffer range、float32 atomic add、vendor id），4 条读 workload（高斯容量、图像尺寸、训练图数量），4 条编码在特定 driver 上观测到的失败（全部 key 在 Qualcomm）。第二步不做设备端计时，用固定 preference order 在剩余可行 schedule 里逐选项取第一个可用值；AMD 与 Intel 各有一份离线定的顺序，其余厂商共用通用顺序。正确性不靠 bit 对齐：定义数值一致性 |q_hat - q| 不超过 eps_abs + eps_rel|q|（q 为梯度或 Adam 更新量），离线把每个可行梯度方法与同卡 reference（exact pair gather）比，再让每设备选中的 schedule 与独立 CPU 双精度实现比，并用故意漏掉一个 tile partial 的负对照证明测试会失败。实现是一个 C++20 训练库加自研小型 Vulkan compute runtime（多 pass program、exclusive scan、headless context、运行时 GLSL 到 SPIR-V），所有梯度手写 kernel，参数、优化器状态与活跃高斯数常驻 GPU 固定容量 buffer，command buffer 录一次反复 replay。桌面、Android 与 iOS 共用同一 core，Apple GPU 走 MoltenVK，RX9070XT 走 Mesa RADV；标准质量设定为 30k updates、SH degree 3、MCMC 细化、100 万高斯容量、0.8 L1 加 0.2(1-SSIM)。上层是 Android（ARCore 采集加 CPU COLMAP 端口）与 iOS（ARKit）的 capture-to-view 应用，采集、SfM、训练与查看全在设备上完成。评测用 Mip-NeRF 360 七个场景、Tanks and Temples 的 Train/Truck、Deep Blending 的 DrJohnson/Playroom，每八帧留一帧，统一 evaluator 算 PSNR/SSIM/LPIPS，每配置三次取中位数。

## 实验与结果
- 八个配置（NVIDIA PRO6000、Intel Iris Xe、Intel UHD730、Arm Mali G1-Ultra、Qualcomm Adreno740、AMD RX9070XT、Apple M5Pro、Apple A14）全部完成 30k updates 与 100 万高斯的 standard-quality 训练
- VkSplat 只在 4/5 个桌面配置完成（UHD730 在前 200 步挂死 GPU），Brush 完成 6/8（Adreno740 超出 128 MiB storage-buffer）
- 跨设备最终质量几乎一致：bicycle 的 PSNR span 0.019 dB（25.28 到 25.30），garden 为 0.063 dB（26.97 到 27.03）
- SSIM 与 LPIPS 变化不超过 0.001
- 训练时间跨约两个数量级：PRO6000 115 s，两台 Android 与 iPhone 2.36 到 3.23 h，UHD730 3.44 h
- PRO6000 11 场景 macro：Cross3DGS 27.86/0.883/0.139、136.8 s
- VkSplat 27.79/0.882/0.143、139.3 s
- Brush 27.90/0.885/0.138、426 s（约 3 倍时间）
- 对 VkSplat 的 PSNR 增益 0.074 dB（95% 区间 0.002 到 0.14），时间差 4.4 s 的区间含 0
- 更新一致性：同卡各可行梯度方法与 exact pair gather 的最大差为 3.4e-8（梯度）与 1.5e-6（Adam），对 CPU 双精度 oracle 的最大差 1.6e-5，零越界
- 负对照（故意漏掉一个 tile 的 partial）产生 29,921 个违规
- 移动端能耗：Adreno740 16.9 Wh（6.0 W）、G1-Ultra 7.2 Wh（3.0 W）、A14 在 25.5k/30k 步约 9.2 Wh
- 应用从采集到可看模型 28 到 46 分钟，SfM（19 到 30 分钟）比 3DGS（7 到 18 分钟）更久

## 创新点与贡献
- 把「可移植」从「换一门着色语言重写 kernel」重构为「同一数学更新加每设备选一条可行 schedule」：256 条 schedule 的目录、13 条读设备限制/workload/driver 的可行性规则、以及不在设备上计时的固定偏好序，使八个跨六厂商的配置都能跑完标准质量训练
- 把正确性形式化成更新级数值一致性测试（含 CPU 双精度 oracle 与负对照），而不是只看 PSNR 是否像样
- 工程上给出同一 C++20 core 经 MoltenVK 与 RADV 覆盖桌面、Android、iOS 的完整链路，以及可用的 capture-to-view 应用

## 局限与风险
- 作者自述固定偏好序是为可预测部署牺牲设备最优速度：每厂商的顺序只在单一设备与 driver 上定，同厂商其他设备可能排序不同
- 通用序在 RX9070XT 与 UHD730 上选出的方法比最快可行方法慢 2.94 与 4.17 倍
- 四条 driver 规则全部 key 在 Qualcomm、只在一个 Adreno740 与一个 driver 上测过，换 GPU 或新 driver 可能误排除本可运行的 schedule（只损速度不损正确性），而未预期的 driver 失败在发生前无法被规则捕获
- 证据范围有限：跨设备质量只覆盖两个场景，11 场景对比只在 PRO6000
- 与 VkSplat/Brush 是系统级比较，视图顺序、优化器状态与 densification 轨迹都不同
- 头显与智能眼镜留作未来工作
