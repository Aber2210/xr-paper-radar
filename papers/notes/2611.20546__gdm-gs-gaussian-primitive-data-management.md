# GDM-GS：面向高效 3DGS 轨迹渲染的高斯基元数据管理框架

## 一句话结论
把锚点选择改写为带洞视锥查询并跨视角共享物化，轨迹渲染较Octree-GS快2.21×　把锚点选择改写为带洞视锥查询并跨视角共享物化，BungeeNeRF 轨迹渲染较 Octree-GS 平均快 2.21×（理论上界 2.73×）。

## 要解决的问题
轨迹渲染是数字孪生与巡检的核心操作，但结构化 3DGS 仍逐视角执行：每视角投影全部锚点做选择，重复解码邻视角已请求的锚点，且三步全在 GPU 而 CPU 空闲。参考时延中的冗余分别落在选择、物化与调度，缺少把一条轨迹的多个视角当作相关查询集合统一优化的机制。

## 方法详解
把轨迹渲染形式化为空间数据管理：锚点=空间对象、视角=范围查询、解码高斯=共享派生数据。① 帧内：为锚点建保守包围盒索引、为遮挡体建索引，把选择变成带洞视锥范围查询，视外与可证被挡锚点不解码；该查询无需投影与解码，可下放 CPU。② 帧间：shared materialization 把连续 K 个视角并为组，取并集后在源位姿下只解码每个不同锚点一次，用成员列把同一行高斯映射到多视角，各视角仍按自身位姿渲染，以有界失真换解码复用。③ 跨处理器：按实测吞吐把一批查询分给 CPU 与 GPU，待整批选择完成再物化渲染；每组按轨迹顺序准入，仅在精确保留行数能放入剩余共享行预算 C 时放行，组末释放，保证显存有界。每视角选择一次、每组物化一次、每视角渲染一次，保持选择到物化到渲染的依赖。

## 实验与结果
- 8 个 BungeeNeRF 场景（1600×900，每场景约 1–1.3M 锚点）：较最强基线 Octree-GS 至少 2× 快，平均 2.21×，接近理论上界 2.73×
- 画质相对 Scaffold-GS（8 场景平均）：PSNR +1.21%、SSIM +1.11%、LPIPS −6.20%
- 空间视锥查询在 2 ms 内定出有用高斯，比 Octree Selection 快近 10×（各场景 7.18–10×）
- 带洞视锥使锚点选择 <1 ms，比完整视锥低 50% 以上；但遮挡体检索 >1 ms 抵消部分收益
- 共享物化：多数场景单视角物化时间降至 K=1 的 1/3 以下；组内 >73% 锚点全视角共享、仅约 4% 独有
- K=4 共享图像仅 1 张未通过质检（PSNR≥40 dB、SSIM≥0.99、LPIPS≤0.01、深度相对 MAE≤1%）

## 创新点与贡献
- 相对 OccluGaussian、Proxy-GS 的逐视角剔除与 GS-Cache、LODGE 的缓存复用，首次把锚点选择形式化为保守界索引上的带洞范围查询，并把跨视角解码复用与 CPU-GPU 划分纳入同一有界内存调度。
- 对比基线：Scaffold-GS, Octree-GS, 参考逐视角执行, GS-Cache（讨论对比）, LODGE（讨论对比）, OccluGaussian / Proxy-GS（讨论对比）

## 局限与风险
- 测试场景多为遮挡较少的通用场景，仅 Amsterdam 与 Barcelona 能剪掉 3 万以上锚点；遮挡体检索耗时超过 1 ms，抵消带洞视锥的选择收益（作者列为后续方向）；共享物化有质量损失，K 越大 PSNR 越低。
- 消融：K=3/4/6 与源位姿对比：K 增大 PSNR 下降，中间帧作源位姿更优；带洞视锥与完整视锥的选择时延对比；三段分解显示物化与渲染已最优，选择归零上限也只有 2.73×，当前 2.21× 已接近。
