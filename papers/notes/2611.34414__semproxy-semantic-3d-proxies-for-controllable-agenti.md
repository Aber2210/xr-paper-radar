# SemProxy：面向可控智能体三维建模的语义三维代理

## 一句话结论
把「语义标签 + 显式 3D 数值」绑成可序列化代理（带标签 OBB 的 JSON + bbox.blend）作为编码智能体的 3D-native 输入，无需编码器与微调——Codex 场景 Chamfer 7.8→3.2、难物体 5.6→2.5，三智能体平均改善 47%，535 份回答中 67.5% 偏好带代理的版本，成本几乎不变。

## 要解决的问题
编码智能体（Claude Code、Codex 等）已能通过几何与建模 API 写代码生成 3D 模型，但用户很难控制过程：现有输入只有文本与参考图，文本难以表达精确的空间意图（部件尺寸、相对布置），图像又常因遮挡而歧义，于是需要反复追加提示。论文举的例子是给书桌显示器增高架改一个深度，就要多一轮对话才能说清；定量上，Codex 在纯文本加图像下建场景的 Chamfer 距离（×10³）为 7.8、难物体 5.6，Claude Code 场景 9.7、DeepSeek 场景 10.5。反过来，把网格或点云这类稠密 3D 直接交给现成编码智能体也不行——用户难以编辑，智能体也无法直接读懂。

## 方法详解
提出「语义 3D 代理」：$\mathcal{P}=\{p_k\}_{k=1}^K$，每个元素把语义（文本标签，可带自由描述）与空间（显式 3D 几何的精确数值）绑在一起，并满足两条要求——3D-native（用户在 3D 里直接摆放拖拽，而非用文字描述）与 agent-native（能无损序列化为结构化文本、也能渲染成图像，因而无需编码器或微调）。实例化为带标签的有向包围盒 $p_k=(\ell_k,\mathbf{c}_k,\mathbf{s}_k,\mathbf{R}_k)$，序列化为 JSON 列表（obb_proxy.json）、同时存为每个盒子一个立方体的 Blender 场景（bbox.blend，按标签命名），换一种代理形式只需替换这两个文件。代理不必完整：用户可只标自己关心的部件或场景物体，其余交给文本与图像。工作区只有 inputs/（prompt.txt、image_N.png 及可选 image_N.txt 说明「从这张图取什么」、obb_proxy.json、bbox.blend）与 outputs/（脚本、渲染、最终模型）；智能体的任务提示要求同时满足文本、图像与盒子的联合期望，并明确盒子是近似参考而非精确目标。方法只固定输入端：用哪个编码智能体、怎么建几何都开放，本文统一用 Blender Python API，评测三个现成智能体（Codex 配 GPT-6.1 Sol、Claude Code 配 Claude Opus 5.5、开源 DeepSeek Harness 配 V4.1 Flash），单次会话上限 120 min。界面 ProxyStudio 负责把 3D 盒子编辑器、文本框与图像卡写成 inputs/、拉起智能体、并在同一视口叠加显示 outputs/。代理可由智能体起草：读文本与图像写盒子到 outputs/、用渲染自检，用户审阅修改后接受，接受的盒子移入 inputs/ 后与手摆盒子完全同权。

## 实验与结果
- Codex 简单物体 Chamfer（×10³）：5.6 降到 4.1；难物体 5.6 降到 2.5；场景 7.8 降到 3.2
- Claude Code：简单 5.5 降到 3.3、难 5.6 降到 2.6、场景 9.7 降到 3.9
- DeepSeek：简单 6.7 降到 4.9、难 6.5 降到 3.8、场景 10.5 降到 3.8
- 三智能体平均：Chamfer 改善 47%、DINOv3 相似度 +2%、Uni3D 相似度 +1.5%
- 成本（Codex，分钟每次）：简单 4.2 到 4.1、难 4.2 到 4.1、场景 4.2 到 4.1；输出 token 7.2k 到 6.7k；DeepSeek 时间 36.6 到 34.6 min、输出 243k 到 217k
- 用户偏好：32 名参与者、535 份回答中 67.5% 选择带语义 3D 代理的模型
- 噪声鲁棒性：10% 位置与尺度扰动加 5° 旋转后仍接近 GT 代理结果、常为次优；30% 噪声时 DINOv3 与 Uni3D 相似度跌破纯文本加图像基线
- 代理编码对比（15 样本子集，三智能体平均）：完整代理 CD 3.2；仅渲染 4.7；文本模板 5.7；LLM 撰写文本 5.9；纯文本加图 7.0

## 创新点与贡献
- 相对以文本与图像为唯一条件的编码智能体工作流（3DCodeBench、3DHarnessBench、ShapeCraft 等），这里把「带标签的 3D 包围盒」作为用户可编辑、且能无损序列化为文本与渲染为图像的条件通道，直接喂给未经修改的现成智能体——不需要新编码器、不需要微调、不扩展建模 API
- 相对 ControlRoom3D 这类用语义代理房间去条件化 3D 生成模型的做法，这里的代理不是给生成模型，而是给通用编码智能体读
- 相对 SpaceControl、HandMade、Prox-E 需要专门生成器或专门 VLM 读取器，这里只依赖「能读文件、能驱动建模工具」这一最小假设

## 局限与风险
- 作者自述两点：定量实验用 GT 网格与 GT 盒子代替用户手摆的代理，因为目前没有大规模「用户摆放 3D 盒子」的数据集，构建成本很高
- SemProxy 面向的是创作型工作流（建模新资产，本身没有真值），恰是它最该发挥作用的场景却无法用参考指标打分
- 从实验看还有别的缺口：只用 Blender Python API 一个后端，未验证 CAD 或程序化建模 API
- 自起草代理全面失败说明「减少用户负担」这一动机在无额外 3D 信息时不成立
- 30% 噪声即跌破基线，代理质量的下限没有刻画
- 用户研究规模小（偏好 32 人、实作 7 人），且参与者 3D 经验从零到丰富不等，未按经验分层报告
- 场景任务只有 20 个房间、每样本一次 trial，方差未知
- 作者另有附录讨论冲突输入、纹理风格与曲面形状的失败情形
